# Blip Builder — Monitoring Events

Documentation of all events generated by `IBlipLogger` in the Builder pipeline.

---

## Common structure

Every monitoring event is emitted as a `LogEntry` by the `BlipMonitoringLogger` library. The entry is built from a `LogInput` (produced by this SDK) plus fields added by the library itself.

### Fields added by the library (LogEntry)

These fields are present in every emitted log entry regardless of the event type:

| Field | Type | Source | Description |
|---|---|---|---|
| `Category` | `string` | Logger method called | Log category derived from the `IBlipLogger` method: `MessageProcessing`, `ActionExecution`, `UserContext`, `ConversationalFlow`, `UserInput`, `MessageDelivery`, `MissingInfoLatency`, `ErrorEvents` |
| `TagSource` | `string` | `[CallerMemberName]` | Name of the `IBlipLogger` method that triggered the log (e.g. `"ActionExecution"`, `"ConversationalFlow"`, `"ErrorEvents"`) |
| `Cluster` | `string` | Library config | Cluster identifier configured in `LoggingOptions` |
| `Exception` | `string?` | `ErrorEvents` parameter | Full exception stack trace; only present on error paths when `ErrorEvents` is called |
| `FlowId` | `string?` | LogEntry | Always `null` — not populated by this SDK (flow identity is tracked via `FlowVersion` and `Data.flowId` in state events) |
| `Tag` | `string?` | LogEntry | Always `null` — not populated by this SDK |

### Fields from LogInput (SDK-side)

These fields are set by the SDK when building the `LogInput` passed to `IBlipLogger`:

| Field | Type | Description |
|---|---|---|
| `Title` | `string` | Event name (see tables below) |
| `EventType` | `string` | Event category: `"ActionExecution"` or `"StateExecution"` |
| `StateId` | `string?` | ID of the current state being processed when the event was generated |
| `FlowVersion` | `int?` | Version of the flow being executed |
| `Channel` | `string` | Source channel domain (extracted from `message.From.Domain`) |
| `IdMessage` | `string` | ID of the message that triggered the processing |
| `From` | `string` | User identity (`userIdentity`) |
| `To` | `string` | Owner identity (`ownerIdentity`) |
| `OriginalFrom` | `string` | Original value of `message.From` |
| `OriginalTo` | `string` | Original value of `message.To` |
| `Operation` | `string?` | Always `null` — not set by any current event |
| `Data` | `JObject` | Event-specific fields (see each section) |

The `IBlipLogger` method called on each event is indicated as **Logger method**. It determines both `Category` and `TagSource` in the emitted entry.

> **Success vs error distinction for action events:** action events call `ActionExecution` on success and `ErrorEvents` on error. The exception is stored in the `Exception` field of the log entry (outside `Data`). State events from `FlowManager` include explicit `success` and `error` fields directly inside `Data`.

## Flow lifecycle events (FlowManager)

### StateProcessingStart

Fired at the beginning of each state processing cycle.

| Field | Type | Description |
|---|---|---|
| `flowId` | `string` | Flow ID |
| `input` | `string` | Serialized content of the input message |
| `stateName` | `string` | Display name of the state being entered |

**Logger method:** `ConversationalFlow`  
**EventType:** `StateExecution`

**Example (complete emitted entry):**

> The library-level fields (`Category`, `TagSource`, `Cluster`, `Exception`) are present in all events. Subsequent examples omit them for brevity — assume they are always present with the values shown here.

```json
{
  "Category": "ConversationalFlow",
  "TagSource": "ConversationalFlow",
  "Cluster": "production",
  "Exception": null,
  "FlowId": null,
  "Tag": null,
  "Title": "StateProcessingStart",
  "EventType": "StateExecution",
  "StateId": "state-greet",
  "FlowVersion": 5,
  "Channel": "wa.gw.msging.net",
  "IdMessage": "a1b2c3d4-0000-0000-0000-000000000001",
```

## Action events

All action events use `ToActionLog` to build `LogInput`, resulting in:

- **EventType:** `"ActionExecution"`
- **Logger method on success:** `ActionExecution`
- **Logger method on error:** `ErrorEvents` (the exception is in the `Exception` field of the log entry, outside `Data`)
- **Common `Data` fields:** `actionId`, `actionTitle`, `elapsedMilliseconds` (present in all action events)

> `actionId` and `actionTitle` are populated from the `$id` and `$title` fields of the action's JSON definition in the flow. They are `null` when not configured.

> `flowId` is **not** present in action event `Data`. The flow context is available through `FlowVersion` and `StateId` in the root `LogInput` fields.
